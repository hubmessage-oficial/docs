## What are webhooks?

Webhooks are HTTP notifications that {projectName} sends to your server when events happen on a channel — such as a message received, delivery status, or connection change.

Instead of your system periodically polling the API, {projectName} **pushes events to you** as they happen.

```
Customer sends message → Hub Message → POST to your URL → Your system processes it
```

<Note>
  Webhooks require the **ENTERPRISE** role on your account. If your account does not have this role, webhook CRUD calls return `422`. Contact support to enable it.
</Note>

## Available events

Not every event exists on every channel. The table below shows which events are emitted by each one.

| Event | When it is triggered | WhatsApp Business | Instagram | Messenger | Telegram Bot |
|---|---|---|---|---|---|
| `MESSAGE_RECEIVED` | A message was received on the channel | Yes | Yes | Yes | Yes |
| `MESSAGE_DELIVERY` | Delivery confirmation for a sent message | Yes | Yes | Yes | No |
| `MESSAGE_STATUS` | Message status update (read, failed, etc.) | Yes | Yes | Yes | No |
| `RECEIVED_STATUS` | Combined received and status | Yes | Yes | Yes | No |
| `RECEIVED_AND_DELIVERY` | Combined received and delivery | Yes | Yes | Yes | Yes |
| `CONNECTED` | The channel was connected | No | No | No | No |
| `DISCONNECTED` | The channel was disconnected | No | No | No | No |
| `PRESENCE_CHAT` | Contact presence or typing indicator | No | No | No | No |
| `INITIAL_DATA` | Template status or category update | Yes | No | No | No |
| `BLOCK` | Contact block event | No | No | No | No |

<Warning>
  Registering an event that does not exist on the channel **does not return an error**. The webhook is created normally, but it never receives anything. Check this table before configuring it.
</Warning>

<Note>
  `INITIAL_DATA` is used for WhatsApp Business template events, such as a status or category change. It does not apply to Instagram, Messenger, or Telegram Bot.
</Note>

<Note>
  The Telegram Bot API does not report message delivery or read status. Therefore, `MESSAGE_DELIVERY`, `MESSAGE_STATUS`, and `RECEIVED_STATUS` are not emitted for this channel — use `MESSAGE_RECEIVED` to know that the customer replied.
</Note>

## Payload formats

The public documentation currently documents one payload format: `DEFAULT`. It delivers the event normalized by Hub Message in the standard webhook envelope.

| Format | Description |
|---|---|
| `DEFAULT` | Standard Hub Message format |


## Webhook authentication

You can configure how {projectName} authenticates when calling your URL:

| Type | How it works |
|---|---|
| `NONE` | No authentication (not recommended in production) |
| `BEARER` | Sends `Authorization: Bearer <token>` |
| `API_KEY` | Sends a configured API key |
| `BASIC` | HTTP Basic Authentication (`username:password`) |
| `CUSTOM_HEADER` | Sends a custom header with a name and value you define |

## HMAC signing

To ensure requests received are genuinely from {projectName} and have not been tampered with, enable HMAC signing by setting `signing: true` when creating the webhook.

When enabled:
- A 64-character hexadecimal `secret` is generated and returned **only once** on create/update.
- Each request sent to your webhook includes a header with an HMAC-SHA256 signature computed over the payload.
- You verify the signature on your server using the stored `secret`.

<Warning>
  The `secret` is shown **only** in the `POST /webhooks` (create) or `PATCH /webhooks/{id}` (update with `signing: true`) response. Store it securely — it cannot be retrieved afterwards.
</Warning>

## Per channel

Each webhook is associated with a specific channel via `channelId`. A single channel can have **multiple webhooks** with different configurations — for example, one for messages and another for connection events.
